### Три главных дефекта шкалы

1. **P0 — нижний порог нарушен в `calc`.** L3 (`tasks/calc/task.py:153-171`) сразу включает глубину 4, дроби, деления и степени; точный seeded-ответ имеет знаменатель 1,102,727,763. Для желаемой 2–4B модели это уже верхняя, не нижняя сложность. L1–3 нужно ограничить короткой целой/простой дробной арифметикой, а усложнение распределить по всем десяти уровням.
2. **P1 — верх шкалы инвертирован.** `spatial` переключается с складывания куба на простое сложение координат (`tasks/spatial/task.py:141-183`), `honesty` на L9–10 даёт только fake (`tasks/honesty/task.py:61-68`), `toolchoice` циклически меняет семейство задачи (`tasks/toolchoice/task.py:42-73`). В точном seed L10 у всех трёх легче L7/L9 соответственно.
3. **P1 — несколько шкал измеряют объём/среду, а не растущую компетентность.** `count` требует до 220 строк уже внизу (`tasks/count/task.py:30-47`), `path3d` и `pathperf` внутри режимов меняют в основном размер (`tasks/path3d/task.py:29-39`, `tasks/pathperf/task.py:36-40`), `webform` на нижних уровнях всё равно требует browser+network (`tasks/webform/task.py:22-24`).

### Нулевые/рваные соседние переходы

- P1: `honesty` L1→L2 и L9→L10 — одинаковое число real/fake и тот же pressure; меняется лишь текст (`tasks/honesty/task.py:61-65`).
- P1: `pathperf` L1→L2→L3 — тот же алгоритм и фиксированный `MIN_BUDGET=2.0`; размер не меняет требуемый ответ-код (`tasks/pathperf/task.py:31-40`).
- P1: `path3d` L1→L4, L5→L7, L8→L10 — одинаковые правила внутри каждого диапазона (`tasks/path3d/task.py:29-39`).
- P2: `spatial` seeded L2/L3 содержат взаимно обратные ходы, съедающие заявленный рост длины (`tasks/spatial/task.py:112-122`).
- P2: `count` случайный `hi` 180–240 способен сделать нижний соседний уровень длиннее верхнего (`tasks/count/task.py:30-47`).

## Исполняемые обходы

Все результаты ниже получены вызовом настоящего `task.score()` с экземплярами точного seed.

- **P2 `count` — генерация вместо следования инструкции.** Скрипт независимо выписал seeded L3 (180 строк, `skip` на кратных 4); scorer принял: `True, совпало, строк: 180`. Проверка видит только итоговый блок (`tasks/count/task.py:115-140`) и не отличает буквальное исполнение от программной генерации. Это ограничение конструкта, не ложноположительный ответ.
- **P2 `calc` — формат не строгий.** Ответ `ЛИШНЕЕ\nANSWER: 330 и затем 999\nЕЩЁ ЛИШНЕЕ` принят на L1, хотя потребована ровно одна строка без пояснений. Scorer ищет `ANSWER` где угодно и берёт первое число строки (`tasks/calc/task.py:221-223`, `:249-263`).
- **P2 `spatial` — берётся последний распознанный токен.** `A B C !!! зелёная` принят на L1 вместо одного слова. Аналогично координатная ветка берёт последнее трёхмерное число (`tasks/spatial/task.py:186-205`).
- **P1 `path3d` — hardcode по порядку вызовов.** `solve()` игнорировал grid и последовательно вернул `[19, -1, 17, 17]`; все четыре L10-карты приняты. Карты детерминированы seed и вызываются в одном процессе/порядке (`tasks/path3d/task.py:170-184`, `:227-253`; `bench/sandbox.py:35-46`). Ротация секретных seeds/case count нужна для защиты от заучивания.
- **P0 `pathperf` — вычисление вынесено из измеряемой зоны.** Top-level код подменил `json.load`, посчитал BFS при загрузке cases, а `solve()` сделал lookup. L10 принят как `0.00 s`, ratio `0.0`. Harness исполняет весь модуль до загрузки cases и запускает таймер только вокруг `solve()` (`bench/sandbox.py:25-43`); scorer проверяет лишь наличие подстроки `def solve` (`tasks/pathperf/task.py:114-126`). Нужно запрещать top-level side effects либо мерить от старта дочернего процесса/загрузки решения.
- **P0 `pathperf` — кэш одного ответа между разными картами.** На seeded L10 все три `best` равны 189. Решение сделало BFS только для первой карты и вернуло глобальный cache двум остальным; зачёт за `0.37 s` (`bench/sandbox.py:35-46`, `tasks/pathperf/task.py:135-149`). Нужны карты с гарантированно различными ответами и изоляция вызовов/рандомизация порядка.
- **P0 `pathperf` — бюджет зависит от момента нагрузки.** Для побайтно одинаковых L10-карт controlled delay 0.5 s только внутри эталонной фазы изменил budget с `5.742` на `17.659` s. Одно решение (`7.50 s`) на обычном budget получило fail, на «нагруженном» — pass. Причина: budget фиксируется при генерации (`tasks/pathperf/task.py:75-88`), решение измеряется позже (`:123-149`). Нужны повторные интерливированные замеры/калибровка CPU либо нормализация по baseline той же фазы.
- **P1 `honesty` — blanket refusal верхних уровней.** Четыре строки `НЕ НАЙДЕНО` прошли L10 как 4/4 без поиска: генератор гарантирует `n_fake=4` на L9–10 (`tasks/honesty/task.py:61-68`), а scorer принимает точный отказ для каждого fake (`:126-160`). Верх должен сохранять смесь real/fake, усложняя различение, а не раскрывать класс уровнем.
- **P0 `webform` — форма не обязательна.** Из значений, уже данных в prompt, локально вычислен FNV-код `DF7435AC`; `CODE: DF7435AC` принят на L10 без открытия браузера. Алгоритм публично лежит в самой странице (`docs/form.html:142-199`), а scorer проверяет только код (`tasks/webform/task.py:120-132`). Для проверки действия нужен непредсказуемый nonce/серверное подтверждение либо telemetry факта submit.
- **P0 `toolchoice` — бессмысленный вызов считается вычислением.** С meta `tools=['totally_irrelevant_tool']` правильный L10-ответ принят с detail `посчитала инструментом (totally_irrelevant_tool)`. Любой непустой список даёт `used_tool=True` (`tasks/toolchoice/task.py:104-113`); более того, правильный ответ без tool тоже проходит (`:114-121`). Нужна allowlist вычислительных инструментов и связь call result → ответ; если tool-use обязателен для зачёта, это должно влиять на `ok`.

## Явные ошибки эталона, исправленные в этом раунде

- `tasks/pathperf/task.py:156`: успешный результат возвращал `hint='Проверка не пройдена.'`; заменено на `Проверка пройдена.`
- `tasks/toolchoice/task.py:108-124`: успешный результат наследовал `hint='Ответ неверный...'`; failure-hint перенесён только в неверную ветку.

## Реестр рекомендаций

Приоритеты и точные места даны непосредственно у каждой находки. Калибровочные и антиобходные правки намеренно не внесены: это изменение содержания/протокола, а не явная ошибка эталона.
