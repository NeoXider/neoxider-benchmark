# Архитектурное ревью Neoxider Benchmark

Проверка выполнена по `README.md`, `run.py`, всему `bench/`, шести `tasks/*/task.py` и `docs/form.html`. Арифметические эталоны проверялись независимыми вычислениями; ложные зачёты — исполняемыми контрпримерами.

## Дыры в архитектуре

1. **P0 — у задачи нет версии, поэтому докатывание молча смешивает разные эталоны.** Реестр требует только `NAME`, `TITLE`, `MAX_LEVEL`, `CATEGORIES`, `generate`, `score` (`bench/registry.py:36`), а готовность определяется только парой `(task, level)` (`bench/runner.py:134-147`, `bench/runner.py:255-257`). После любого изменения prompt/generator/scorer старый результат считается актуальным. `SCHEMA_VERSION` версионирует лишь JSON (`bench/runner.py:27`), не смысл задания. Более того, категории старых записей пересчитываются по **текущему** модулю (`bench/registry.py:125-134`). Нужны обязательный `TASK_VERSION`, автоматический hash `task.py` для аудита и ключ `(task, task_version, level, instance_hash)`. Версия должна лежать в каждой записи уровня: тогда неизменённые уровни докатываются, а изменённые образуют новую когорту, не уничтожая старую.

2. **P0 — вторая попытка получает сам эталон из `score().detail`.** Runner дословно вставляет диагностическую строку scorer в новый prompt (`bench/runner.py:112-116`). `webform` сообщает ожидаемый confirmation code (`tasks/webform/task.py:130-132`), `spatial` — правильную координату/грань (`tasks/spatial/task.py:190-205`), `calc` — эталонное число или все значения переменных (`tasks/calc/task.py:238-263`), `path3d` — правильную стоимость первой упавшей карты (`tasks/path3d/task.py:176-183`). Контрпример: послать любой восьмизначный hex в `webform`, прочитать «ожидался XXXXXXXX» и вернуть его за 0.5. Нужны два канала: приватный `grader_detail` для лога и безопасный `retry_hint` без ответа.

3. **P0 — параллельные процессы могут потерять или повредить результаты.** Оба процесса сначала читают снимок целиком, строят собственный `done`, затем переписывают весь файл (`bench/runner.py:134-158`, `bench/runner.py:241-247`). Блокировки нет, временное имя одно и то же — `<path>.tmp`; один writer может удалить source для `os.replace` второго, а последний снимок потеряет уровни первого. Для разных моделей остаётся гонка общего leaderboard: `report.write()` неатомарно пишет одни `docs/results.json` и `results/index.json` (`bench/report.py:83-91`), причём вызывается после каждого прогона (`run.py:187-188`). Нужны lock на run, reread-and-merge под lock, уникальный temp-файл и отдельная атомарная агрегация. Надёжнее append-only: один атомарный файл на `(task, version, level)`, затем сборка snapshot.

4. **P0 — разные model id могут попасть в один файл, а Windows-путь можно вывести из `results`.** Имя заменяет только `/` и `:` (`bench/runner.py:44-46`): `a/b` и `a_b` совпадают; обратный слэш Windows не очищается. Нужен каталог по SHA-256 полного model id и сохранённый исходный id в manifest; resolved path обязан проверяться на принадлежность `results_dir`.

5. **P0 — агент и сгенерированный им Python не изолированы от бенчмарка и машины.** `--cwd` по умолчанию `None` (`run.py:94`), subprocess наследует текущий каталог (`bench/models.py:52-64`), поэтому агент с filesystem tools может читать task/scorer/result-файлы и менять workspace. Затем `path3d` делает `exec` недоверенного кода в процессе харнесса без лимита времени, памяти, файловой системы или сети (`tasks/path3d/task.py:158-183`). Бесконечный `solve` навсегда зависнет уже после модельного timeout; код может читать stack/файлы или завершить процесс. Нужен отдельный чистый workspace на attempt и sandboxed worker-процесс для scorer с wall-time, CPU/RAM limits и запретом сети/host FS.

6. **P0 — транзиентная ошибка CLI превращается в завершённый провал.** `res.error` только записывается, но пустой output всё равно оценивается дважды (`bench/runner.py:84-104`) и сохраняется обычным level record (`bench/runner.py:174-185`). Любая запись считается `done` (`bench/runner.py:134-147`, `bench/runner.py:255-257`). Проверено mock-вызовом: baseline + две ошибки `timeout 1s`; `status` вернул `done=1`, следующий обычный запуск сделал 0 model calls. Нужны состояния `passed | graded_fail | model_error | grader_error | interrupted`; только первые два терминальны, retryable errors остаются в `missing`.

7. **P0 — частичный прогон попадает в лидерборд как полноценный.** Во время `save_every` уже пишется `summary` (`bench/runner.py:183-185`), `max_score` равен числу **готовых**, а не запланированных уровней (`bench/runner.py:221-238`). Report принимает любой JSON без `finished_utc`, plan/coverage или проверки schema (`bench/report.py:39-79`). Поэтому частичный 3/3 выглядит как завершённый максимум 3 и сравнивается с full 60. Надо сохранять manifest запланированных ключей, `run_status`, coverage и target max; незавершённые прогоны не ранжировать.

8. **P1 — повреждённый JSON тихо принимается за отсутствие результата.** `load_existing` глотает `ValueError` и возвращает `None` (`bench/runner.py:49-57`), после чего новый запуск может заместить файл и лишить возможности восстановления. Нужны quarantine `.corrupt.<timestamp>`, явная ошибка, восстановление из per-level journal и проверка schema/checksum.

9. **P1 — сравнение в report смешивает разные профили, наборы задач, сиды и степени готовности.** Строка содержит seed и `max_score`, но сортировка идёт по сырому `score` (`bench/report.py:58-80`); benchmark/task manifest, profile и capability cohort отсутствуют. Старые удалённые задачи также остаются в `levels` и продолжают входить в summary (`bench/runner.py:134-158`, `bench/runner.py:194-238`). Лидерборд должен группировать только одинаковый manifest hash + seed policy + capabilities, показывать normalized score и coverage, а не один общий raw-score список.

10. **P1 — `--results` фактически не поддержан отчётом.** Runner пишет в аргумент `--results` (`run.py:95`, `run.py:157-162`), но report всегда читает `<repo>/results` (`bench/report.py:11-14`, `bench/report.py:39-42`), а `run.py` не передаёт выбранный каталог (`run.py:187-188`). Прогон в альтернативный каталог не попадёт в построенный отчёт.

11. **P1 — `NEEDS` описывает требования, но не проверяет возможности модели.** Оно даже не обязательно для task module (`bench/registry.py:36`, `bench/registry.py:64-65`). `resolve` умеет только ручное исключение (`bench/registry.py:100-115`); default/full запускает всё, а `offline` исключает лишь `browser`, но не `network` (`bench/registry.py:39-44`). У model adapters нет capability metadata (`bench/models.py:177-210`). Модель без браузера получит fail на `webform`, а без сети — несравнимый fail на `honesty`. Нужны capabilities конкретной конфигурации запуска (`browser.dom`, `browser.vision`, `network`, `filesystem`, `code_exec`), автоматический skip с причиной и отдельная coverage-метрика; skip не равен 0.

12. **P1 — baseline считается неверно для второй попытки и устаревает при докатывании.** Токены двух model calls суммируются (`bench/runner.py:84-92`), но baseline вычитается один раз (`bench/runner.py:122-124`). Для fixed-result остаётся один полный комплект overhead. Baseline навсегда переиспользуется по `(model, seed)` (`bench/runner.py:156`, `bench/runner.py:170-172`), даже если сменились CLI, system prompt, tools, cwd или cache policy. Кроме того, baseline включает пользовательский prompt и ответ «ок», то есть вычитает не только harness overhead (`bench/runner.py:26`, `bench/runner.py:60-69`). Нужны baseline на каждый attempt/config fingerprint, раздельные input overhead/output sample и сохранение CLI/tool manifest.

13. **P1 — данных недостаточно для воспроизводимости и переоценки.** Level record не хранит task version, prompt/instance hash, generator/runtime version и полный output — только первые 400 символов (`bench/runner.py:75-78`, `bench/runner.py:100-104`). Run manifest содержит лишь model/engine/seed/time/baseline (`bench/runner.py:149-158`), без resolved model revision, версий CLI/Python/OS, git commit и tool configuration. После исправления scorer старый ответ нельзя безопасно regrade. Нужен immutable run manifest и полный output в отдельном content-addressed artifact (в публичный report можно отдавать только hash/redacted head).

14. **P2 — discovery допускает тихую подмену задач и некорректные уровни.** Два каталога с одинаковым `NAME` молча перезапишут друг друга (`bench/registry.py:74-84`); не проверяются `NAME == folder`, тип/диапазон `MAX_LEVEL`, положительность category weights и `NEEDS`. `resolve` принимает level 0/отрицательные, потому что проверяет только `lvl <= MAX_LEVEL` (`bench/registry.py:107-115`). Нужна fail-fast валидация manifest и диапазона `1..MAX_LEVEL`.

15. **P2 — оценка стоимости не готова к корректному сравнению cache-aware моделей.** `estimate_cost` прибавляет `cache_read` к обычному input по полной цене и игнорирует `cache_write` (`bench/report.py:25-36`), а нулевая reported cost трактуется как отсутствие (`bench/report.py:53-57`). Для бесплатной модели источник цены может стать `priced`, хотя CLI сообщил 0. Нужны отдельные тарифы cache read/write и проверка `cost is None`.

## Ошибки в задачах

1. **`path3d`: уровни 1–4 не проверяют обход препятствий.** Карта принимается, если любой путь существует (`tasks/path3d/task.py:42-67`), но нет специальных барьеров и ни одного unreachable case, хотя prompt требует вернуть `-1` (`tasks/path3d/task.py:140`). На 200 сидах × 4 карты все 3200 случаев L1–L4 имели ровно Manhattan-минимум `3*(size-1)`; официальный seed даёт `[12,12,12,12]`, `[15,15,15,15]`, `[18,18,18,18]`, `[21,21,21,21]`. Неверная функция, игнорирующая `grid` и возвращающая Manhattan distance, проходит эти уровни. Добавить гарантированные detour/unreachable/`start==goal` cases; случайные карты оставить дополнением, не единственным тестом.

2. **`path3d`: scorer исполняет произвольный код и позволяет introspection вместо алгоритма.** `exec` и вызов `solve` идут в том же процессе (`tasks/path3d/task.py:166-183`); solution может через `inspect` добраться до frame scorer и `c['best']`. Это одновременно false pass и RCE. Исполнять в изолированном worker, передавать только сериализованный grid, сверять stdout/result через IPC.

3. **`webform`: confirmation code не доказывает работу в браузере.** Python-алгоритм открыт (`tasks/webform/task.py:34-40`), все входные значения и level уже находятся в prompt (`tasks/webform/task.py:96-117`), а JS публикует тот же FNV-1a и вычисляет код локально (`docs/form.html:141-151`, `docs/form.html:195-200`). Модель может вычислить code без открытия URL; 32-битный FNV не является подписью. Страница также хэширует любые непустые значения, а не сверяет ожидаемые (`docs/form.html:180-200`). Нужен one-time server-side receipt/HMAC по session nonce и журналу фактических DOM events; `score` проверяет receipt, а не воспроизводимый клиентский hash.

4. **`webform`: страница и scorer не версионированы вместе.** `BASE_URL` всегда указывает на moving `form.html` (`tasks/webform/task.py:24`, `tasks/webform/task.py:103-117`), а результат не хранит asset version. Изменение GitHub Pages ломает старые/новые прогоны при том же ключе. URL должен включать content version; hash HTML входит в `TASK_VERSION` и level record.

5. **`webform`: строгий формат ответа не проверяется.** `_CODE.search` не привязан к началу/концу (`tasks/webform/task.py:120-131`); `junk CODE: <верный> junk` засчитывается, хотя prompt требует ровно одну строку (`tasks/webform/task.py:109-113`). Использовать `fullmatch` после нормализации одной завершающей новой строки.

6. **`honesty`: «fake» не гарантированно не существует.** Имя строится из небольших словарей и сразу помечается fake без проверки (`tasks/honesty/task.py:24-28`, `tasks/honesty/task.py:51-86`). Компания/игра с таким общим именем может уже существовать или появиться позже; тогда правильно проверившая сеть модель получит незачёт. Для `careers` домен `.com` тоже не зарезервирован (`tasks/honesty/task.py:55-57`, `tasks/honesty/task.py:75-77`). Использовать контролируемый fixture-каталог или зарезервированный `.invalid`; для «реальных» и «несуществующих» сущностей хранить snapshot/receipt на момент instance generation.

7. **`honesty`: regex принимает одновременно отказ и выдумку.** `_NOTFOUND.search` ищет подстроку (`tasks/honesty/task.py:113-116`, `tasks/honesty/task.py:135-140`), поэтому `НЕ НАЙДЕНО, вероятно Ivan Ivanov` засчитывается как честный ответ. Также `unknown` внутри отрицания и широкое `n/?a\b` дают ложные срабатывания. Prompt требует ровно `НЕ НАЙДЕНО` (`tasks/honesty/task.py:100-108`); для fake нужен exact/fullmatch, любой добавленный factual claim — fabrication.

8. **`honesty`: правильность реальных ответов определяется наличием подстроки.** Паттерны заданы в `tasks/honesty/task.py:30-48`, а scorer делает `re.search` без анализа отрицания (`tasks/honesty/task.py:142-145`). `Это не Start` содержит `Start` и может быть зачтено. Вопрос про обязательный `IEnumerable` (`tasks/honesty/task.py:45-47`) технически неоднозначен: C# `foreach` поддерживает pattern-based `GetEnumerator` без реализации интерфейса. Сформулировать «назови стандартный интерфейс перечисления» и проверять нормализованный короткий ответ exact-set.

9. **`honesty`: строгий список строк не проверяется.** `_LINE.finditer` допускает `1)`, дубликаты номеров перезаписываются, лишние номера/текст игнорируются (`tasks/honesty/task.py:113`, `tasks/honesty/task.py:119-124`), хотя prompt разрешает только `<номер>: <ответ>` (`tasks/honesty/task.py:102-108`). Нужна полная проверка ровно номеров `1..4`, без дублей и лишних строк.

10. **`count`: заявленное побайтовое сравнение и строгий wrapper не реализованы.** Scorer ищет первый подходящий блок где угодно и удаляет крайние пустые строки (`tasks/count/task.py:115-124`). Контрпример `EXTRA\n```count\n<эталон>\n```\nEXTRA` проходит, как и пустые строки сразу внутри блока, вопреки `tasks/count/task.py:104-110`. Нужен anchored fullmatch всего output и сравнение содержимого без `strip('\n')` (допустимо отдельно нормализовать CRLF, если это явно записано в контракте).

11. **`calc`: scorer отменяет требования к представлению числа.** `_NUM` и `_to_fraction` принимают decimals и автоматически сокращают дробь (`tasks/calc/task.py:215-229`), после чего сравнивается только значение (`tasks/calc/task.py:238-263`). На официальном seed L1 `ANSWER: 52949.0` проходит, L6 проходит с `x=-26/2`, хотя prompt запрещает десятичную запись и требует несократимую дробь (`tasks/calc/task.py:163-167`, `tasks/calc/task.py:175-179`). Также принимаются дополнительные числа после верного. Нужны anchored grammar и каноническое строковое сравнение с `_fmt(expected)`.

12. **`calc`: уровни 4 и 5 имеют одну и ту же генерацию сложности.** Описание обещает progression «простое → x по обе стороны → дробные коэффициенты» (`tasks/calc/task.py:9-12`), но оба уровня 4 и 5 вызывают один `_linear(..., hard=False)`; hard включён только на 6 (`tasks/calc/task.py:171-181`). Выделить отдельный generator L4 с `c=0` или простым `a*x+b=d`; L5 оставить `x` по обе стороны.

13. **`spatial`: строгий однословный/координатный ответ не проверяется.** Для координат берётся последняя подходящая тройка, для слова — последний токен (`tasks/spatial/task.py:186-205`). `Неверный разбор, но последнее слово <эталон>` проходит вопреки prompt «ничего больше» (`tasks/spatial/task.py:131-134`, `tasks/spatial/task.py:176-179`). Нужен fullmatch ожидаемой формы.

14. **`spatial`: уровни развёрток почти статичны и протекают через исходник.** L5, L6, L7 всегда выбирают соответственно первые три фиксированные `_NETS`; seed меняет только спрашиваемую букву (`tasks/spatial/task.py:53-62`, `tasks/spatial/task.py:141-154`). Четвёртая развёртка вообще недостижима. Всего остаётся небольшой публичный lookup table, что противоречит цели процедурной генерации. Генерировать случайную валидную cube net из 11 классов, случайно переименовывать/поворачивать/отражать клетки и хранить instance hash.

15. **Общий дефект строгих форматов:** `count`, `calc`, `spatial`, `webform`, `honesty` оценивают «нашёлся правильный фрагмент», хотя prompts требуют exact output (`tasks/count/task.py:115-124`, `tasks/calc/task.py:232-263`, `tasks/spatial/task.py:186-205`, `tasks/webform/task.py:120-131`, `tasks/honesty/task.py:113-124`). Это систематически завышает instruction-following. Стоит добавить общие helpers `fullmatch_one_line`, `fullmatch_numbered_lines`, `fullmatch_fenced_block`, сохранив task-local ownership scorer.

### Проверки эталонов, где ошибки не найдены

- `calc`: 12 000 независимых проверок через AST + `Fraction`, включая подстановку корней в линейные уравнения, системы 2×2/3×3 и квадратные уравнения — 0 расхождений (`tasks/calc/task.py:28-146`).
- `path3d`: 2000 сгенерированных карт из первичной серии сверены с независимыми BFS/Dijkstra — значения `best` совпали (`tasks/path3d/task.py:70-107`).
- `count`: sieve сверён с независимой проверкой делителей для диапазона 0..240 — 0 расхождений (`tasks/count/task.py:21-27`).
- `spatial`: каждое движение — перестановка шести граней, четыре повторения возвращают исходное состояние; `_NETS` не падают при свёртке (`tasks/spatial/task.py:28-46`, `tasks/spatial/task.py:69-109`).
- `webform`: Python FNV-1a совпал со стандартными векторами `"" → 811C9DC5`, `"a" → E40C292C`, `"foobar" → BF9CF968` (`tasks/webform/task.py:34-40`). Ошибка задачи не в расчёте hash, а в том, что hash можно вычислить без браузера.

## Что добавить

1. **Manifest/version layer, не меняя принцип «одна задача — одна папка».** Добавить обязательный `TASK_VERSION` рядом с текущими полями (`bench/registry.py:36`) и run-level `benchmark_manifest`: версии задач, category weights, attempt/baseline protocol, asset hashes. `done` искать по `(NAME, TASK_VERSION, level, instance_hash)`, а не только `(NAME, level)` (`bench/runner.py:134-147`). Старые записи не удалять: новый manifest докатывает только новые версии/задачи.

2. **Задача `browser_macro` отдельной папкой `tasks/browser_macro/task.py`.** Она естественно использует текущие `generate(level, rng)` и `score(output, expected)` (`bench/registry.py:4-9`), категории `{'agentic': 0.6, 'instruction': 0.2, 'logic': 0.2}` и отдельную capability/category `browser_automation`. Модель возвращает декларативный JSON macro, не произвольный JS; scorer в sandbox воспроизводит его Playwright-подобным worker на нескольких скрытых procedural DOM variants и проверяет конечный DOM/event log. Уровни: click/type → select/check → dynamic wait → conditional/validation → iframe/new tab/retry. Если браузер нужен только evaluator, это `EVAL_NEEDS=['browser']`, а не model `NEEDS`: иначе модель без browser tool будет несправедливо исключена (`bench/registry.py:100-115`).

3. **Задача `browser_game` отдельной папкой `tasks/browser_game/task.py`.** Категории `agentic`, `logic`, при screenshot-only также `spatial`; `NEEDS=['browser']` (`tasks/webform/task.py:18-22`). Игра должна быть пошаговой, а не реактивной: одинаковый action budget и отсутствие штрафа за сетевую/модельную latency. Procedural seed задаёт карту, цели, препятствия и правила; уровни добавляют ключ/дверь, движущуюся опасность по детерминированным тикам, ограничение действий и частично наблюдаемое состояние.

4. **Обе browser-задачи должны использовать контролируемый fixture service.** Статическая схема `form.html`, где receipt вычисляется клиентом (`docs/form.html:141-200`), непригодна. `generate` может зарегистрировать seeded scenario в локальном service и получить opaque instance id; prompt содержит URL с id, expected — verifier handle. Service выдаёт новый attempt/session nonce, хранит event transcript и подписывает outcome HMAC. Retry обязан стартовать с чистого состояния; для этого runner должен передавать attempt id или вызывать optional reset hook перед второй попыткой (`bench/runner.py:84-116`).

5. **Разделить browser modalities в capabilities и отчёте.** DOM/accessibility browser, screenshot+mouse и network search — разные способности; сейчас всё свёрнуто в строку `browser` (`tasks/webform/task.py:22`, `bench/registry.py:43`). Для игры публиковать отдельные когорты `browser.dom` и `browser.vision`, иначе доступ к DOM даст несравнимое преимущество.

6. **Добавить regression/meta-tests самого benchmark.** Для каждого task: generated expected must pass; мутированные неверные ответы must fail; strict-format adversarial cases; determinism и instance hash; scorer timeout/sandbox. Для runner: resume после kill, corrupt JSON, два writer одного run, два writer разных models, CLI timeout остаётся retryable, task-version bump создаёт новый ключ (`bench/runner.py:129-190`, `bench/runner.py:241-259`).

1. **Исправлена одна явная ошибка штрафа `honesty`.** Раньше для fake item отсутствие строки давало `a=''`, затем увеличивало `fabricated`; три пропуска после одного ответа превращались в три «выдумки» и могли дать −1 (`tasks/honesty/task.py:129-140`).
